# Traveler next steps and current/upcoming stays

Convex remains the backend. Furnished Finder's [traveler What's Next guide](https://support.furnishedfinder.com/hc/en-us/articles/50373304408731-Using-the-What-s-Next-Panel-on-the-Traveler-Home-Screen) (updated May 15, 2026; checked October 26) describes replying to messages, profile setup, resuming searches and finding rentals. Its [saved-search guide](https://support.furnishedfinder.com/hc/en-us/articles/35735878424859-How-to-Save-a-Search) describes preserving criteria for reopening. The app previously lacked traveler next-step cards and hardcoded active/upcoming stay counts to zero.

`travelerDashboard.account` derives the active account from authentication and reads only the latest private saved search and saved-rental record through owner indexes. It offers optional profile introduction, full-criteria search resumption (or search setup) and saved-rental review/comparison actions. Legacy malformed saved criteria link to management instead of failing the dashboard. A profile introduction save removes its optional task reactively. Inbox reply guidance uses the existing native inbox summary only once its migration/folder state is ready; it does not pretend cached/loading counts are complete.

`travelerDashboard.stays` pages at most ten accepted inquiry records for the current authenticated traveler through `(tenantId, status, moveOut)` with a server-current UTC end bound. Current versus upcoming classification uses validated date-only UTC intervals. Pending/cancelled/declined/withdrawn and ended records remain in inquiry management. Property-owner bindings are checked before showing a property title. Invalid dates/references are labelled for review rather than parsed or counted as valid stays. Each accepted record rechecks its actual linked booking calendar; missing/mismatched coverage warns and links to private stay management, while preserving the existing accepted inquiry. Counterparty email/phone, message, street/ZIP and owner draft content are not returned.

The home displays real active/upcoming metrics for loaded stay records and states this scope. Complete paging exposes every current/future accepted record; partial pages are not presented as account totals. Stay cards link to their exact management routes. Next-step guidance includes a loaded accepted stay, prioritizing any needing calendar attention. These are app-accepted inquiry records, not proof of lease signature or payment.

Native account responses include checked time/current UTC day/next boundary. An opaque ignored refresh key invalidates subscriptions on focus/visibility return and a timer calculated from native boundary/check time. Device time does not choose classification. If paged rows span different native days, the client resets and refreshes rather than mixing their metrics. Background/browser timer delays can defer refresh; the checked time remains explicit. Missing app profiles get a setup action. The introduction anchor and accessible textarea label resolve the task directly.

Validation: 497 tests / 45 files, TypeScript, Next production build and both development Convex pushes pass. Seven new cases cover auth/account selection/offboarding/privacy; accepted active/upcoming and calendar status; 127 stays over thirteen bounded pages; native saved criteria and profile-task resolution; server UTC rollover/ignored clock keys; malformed property/date references without foreign draft titles; and malformed legacy saved-search fallback.

`scripts/local-traveler-dashboard-smoke.mjs` guards loopback anonymous deployment, exact dummy billing and disabled email, then uses normal native inquiry/confirmation to create one current and one future synthetic accepted stay under explicit local publication prerequisites. The new dashboard finds both through complete pages with matching calendars and exact private links. Cleanup cancels both, removes only the exact QA rental and confirms its records leave this dashboard; labelled cancelled history is retained. This is privileged synthetic local authentication and not an actual hosted stay/provider/Clerk browser booking. Receipt: `docs/evidence/local-traveler-dashboard-native.json`.

`scripts/hosted-traveler-dashboard-fixtures.mjs setup|check|cleanup` uses only the dedicated development Clerk instance, reserved test email/external ID and normal private profile/saved-search APIs with email delivery disabled. No bookings, contacts, public rentals, paid or identity grants are imported. Actual traveler browser/private state and cleanup are recorded separately. Positive hosted stay cards and unread-reply actions, actual provider workflows, broad public/production acceptance and the subsequent editable Wander/Figma phase remain open.
