# Grouped property lead offers

Convex remains authoritative. The owner receives one lead per housing request and chooses a specific rental space; grouped properties label their units. Indexed suggestions rank recorded exact fit, differences, requested city, bedroom fit and rent. Every visible option and submission rechecks current eligibility. Stored ranking is refreshed on match reconciliation; it is not a real-time price sort. Legacy adoption runs in pages of 25 without creating new leads, messages or activity. Versioned selectors preserve existing pre-upgrade pagination cursors.

One first response is committed atomically per owner/request. Retrying the same space returns its conversation; another space cannot create a second first response. Continue conversation remains available after the rental becomes private. Legacy response markers are adopted only when participants and rental agree; missing timestamps stay unknown, and corrupt history blocks new first replies pending support review. Requests for separate agency travelers retain their own native request and date bindings even if the conversation is shared.

The initial message names its request, requested dates, offered unit, listed monthly rent, and explicit proposal/no-booking status. Partial offers retain the acknowledged differences. The text budget includes this context. A participant-only offer resolver uses the native message/request binding, never parsed text. The deliberate View offered rental action carries original dates into the rental page; travelers cannot use it to view an unpublished rental. Owners can preview their own rental. The proposal does not reserve dates or create a booking.

Phone disclosure is a separate selected-rental query. An old exact delivery never grants phone access to an alternative, hidden, stale or foreign unit. It requires current exact eligibility, open/future request, consent, unchanged phone revision, unexpired verification and no block. The browser hides disclosure when proof or request-day eligibility expires. Raw lead-inbox responses contain no phone number.

Validation: 379 tests across 36 files, TypeScript and Next build pass. Twelve offer cases cover races, retry, legacy compatibility, corrupted bindings, agency travelers, ranking beyond the first page, body budgets and contact expiry. The twenty-fifth native local flow checks actual grouped public options and mutations with explicitly synthetic local publication prerequisites; it restores borrowed receipt-bound QA capacity. Actual Clerk development reads use an explicitly privileged private history fixture; they prove legacy lookup, private contact/send denial, participant/date-bound links and owner rendering, not real cloud public-offer creation. No paid/identity cloud exceptions or real mail/SMS are used. Broad hosted public-offer and provider acceptance remain open.

Reference: [Furnished Finder response guidance](https://support.furnishedfinder.com/hc/en-us/articles/51343862893083-Tips-on-Responding-to-Booking-Inquiries-and-Tenant-Leads). No reference UI styles or third-party source copied.
