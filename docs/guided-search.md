# Guided rental search

This implements the native one-description → review → real search flow. It is not a chatbot and does not generate properties, listing rankings or match counts. Standard search remains available. Visual styles use the existing application's controls; no clone/reference styles or code were imported.

Primary functionality reference: https://support.furnishedfinder.com/hc/en-us/articles/48369373873051-Using-Find-It-With-Fern-Our-AI-Search-Tool. Its current guide describes a single request, summary review, actual matching listings, applied filters, manual edits and Refine preferences. The live guided route was available to web research only as a loading/beta shell; no gated interaction is claimed.

## Runtime and activation

`convex/guidedSearch.ts` uses the existing Convex backend and documented `getServiceToken("ai-gateway")` in an action. It calls only `https://ai-gateway.convex.dev/v1/chat/completions`, with `openai/gpt-4o-mini`, strict JSON Schema output, a 1,600-token output cap, twenty-second network timeout, redirect rejection and a 128 KiB response limit. No new package, external skill, model SDK, database service or provider secret was installed/acquired.

The operator must set `AI_SEARCH_ENABLED=1` on the intended Convex deployment, and that team's gateway must actually be available. A token-only availability probe never calls a model or exposes credentials. The current `cheerful-ferret-182` development deployment returns `{available:false, reason:"provider_unavailable"}`. The disabled interpretation guard also passed natively. No model was called, paid plan changed or other product's key borrowed. Source/provider mocks are not live inference acceptance. The official gateway requires a paid plan; changing billing or selecting an alternative app-specific model provider remains an owner decision.

Do not enable the feature simply to make the availability label turn green. First establish the intended provider/billing setup, then validate real model interpretations, refusal/timeout behavior, browser review and actual native search results. Keep development and production configuration separate. Existing Convex team billing/usage warnings were not resolved or bypassed.

Official contracts: https://docs.convex.dev/ai-gateway/overview, https://docs.convex.dev/ai-gateway/setup and https://docs.convex.dev/ai-gateway/api. The integration requests `zdr:true`, `data_collection:"deny"`, `require_parameters:true` and prompt/completion price ceilings. These are provider-routing policies, not a guarantee that platform usage/billing metadata disappears. There is no application prompt/conversation table or console logging of prompts/results/credentials. The hosting/backend platforms may retain their normal operational metadata.

## Interpretation and review

- Inputs are 10–2,000 characters, with consent to process the description/current filters through AI. User/account switches remount the private editor and invalidate pending UI responses. Review controls lock during interpretation; there are no tools, conversation history, model-supplied URLs or model-supplied geometry.
- The model receives current native filters and unresolved preference notes as one request's context. Its output is validated again in code, including field names, types, allowed features, valid dates, conflicts and limits. The server calculates exact day/week/calendar-month checkout dates, including month-end clamping; it rejects stays below the native thirty-day minimum and past dates. Dates incomplete for availability remain explicit unapplied notes, including the requested duration.
- City/state, monthly USD rent, minimum bedrooms/bathrooms/occupancy, supported property types, amenities, booleans and stay dates feed the existing `normalizeSearch`/URL/query path. Negative booleans are retained. Exact room counts, workplace/ZIP/neighborhood proximity, travel time, non-USD prices and unsupported requirements must remain unapplied, rather than be falsely claimed as satisfied. Geometry comes only from the existing manual location/map flow.
- The visible summary is derived from normalized filters rather than model-written claims. Users can edit city/state/property, dates/flexibility, location/radius, types, budget, capacity and amenities. Unapplied notes require explicit acknowledgement before proceeding without those guarantees. Changing the description requires a fresh interpretation before applying its old summary; standard search remains an exit.
- See my matches opens the existing search engine. Visible applied-filter chips and Refine preferences preserve the actual criteria in the URL. Raw descriptions and consent are not placed in URLs or saved searches. Owner-described amenities and approximate distances remain subject to listing review.

## Limits and evidence

Atomic claims enforce one in-flight request per actor, five attempts per minute, thirty per UTC day and one hundred total per deployment per UTC day. Native signed identities determine account limits even if page IDs rotate. Anonymous page references are client supplied, so they are not an abuse-proof identity; the deployment-wide cap limits that exposure. These are request-count ceilings, not a dollar spending limit. A day's bounded request-ID history rejects repeated submissions; failed attempts still consume the allowance, and no provider call is retried automatically. Rate records store a hashed reference, counters, IDs and busy-until time, not descriptions or interpretations. A bounded daily/continuation cleanup removes inactive records older than three days.

Fifteen focused cases cover schema/date/feature rejection, duration calculations, unresolved preferences, summary/URL/native filter behavior, consent/configuration/access guards, fixed-origin privacy parameters, source-to-native empty search, concurrency, historical replay, minute/day/global limits, signed-account page rotation, bad/refused/truncated/oversized/provider-failed output, bounded cleanup and release after failures. Provider calls and token minting are mocked in these cases. Actual cloud availability/configuration guards are recorded in `docs/evidence/hosted-guided-search-provider.json`. Real interpretation quality, costs, provider policies and full anonymous/authenticated/mobile rendering still require acceptance after activation.
