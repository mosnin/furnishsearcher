# Deleting tenant leads

An owner can permanently remove a delivered matched or unmatched lead from Tenant Requests. The confirmation identifies the traveler and area, states that the lead cannot be restored, and explains the effects. Keep lead, Escape and closing the dialog cancel without a write. The submit stays pending until the native mutation acknowledges; errors remain in the dialog. Other cards stay independent.

Convex authorizes the exact delivery owner, marks an immutable deletion timestamp and makes retries inert. There is no restore endpoint. This is owner-specific lead removal, not deletion of the traveler's housing request or an account erasure operation. Other owners can still respond, and a separately created new request is independent. Existing conversations, messages, inquiries, stays and their history remain available under their existing permissions. Historical match/performance records are not decremented. A minimal native delivery marker remains to prevent redelivery; it is not exposed as a recoverable deleted-leads folder.

The inbox skips removed leads while preserving native pagination. Empty filtered pages can still have older requests, so Continue loading remains available. Stale clients receive no match options or phone details and cannot mark the deleted lead read or create another first response. All owner/request/listing scans consult the marker before inserting new matches, incrementing activity or queueing notifications. Re-enabling unmatched intake does not revive a removed lead.

Deletion atomically suppresses and fences unclaimed queued email work. Eligibility is checked again during notification selection and provider-attempt claiming, including legacy notification reads. Already claimed/sent attempts retain their generation, provider outcome and idempotency audit: deletion cannot recall a message already being sent. No notification preference changes and no global traveler block are implied.

Validation: eight additional native backend cases cover ownership, retries, preserved native inquiry/message/request records, fresh phone denial, new-rental and owner rescans, independent owners/requests, unmatched intake changes, queued selection/claim/recovery, claimed provider result retention and 30-lead paging. All 387 tests across 36 files, TypeScript and Next production build pass. The guarded local deletion mode runs actual public-unit/contact/first-response/deletion/scan APIs using explicit synthetic local publication prerequisites; fixtures return hidden, the request closes and borrowed receipt-bound QA capacity is restored. Actual Clerk development acceptance uses a new disposable traveler and explicitly privileged private historical lead; this does not claim real paid/identity/SMS/provider or public hosted offer acceptance. Browser acceptance opens and cancels the permanent-deletion confirmation; final removal is exercised separately through native APIs. No real mail/SMS or production/customer records are changed.

Reference: [Furnished Finder: deleting a tenant lead](https://support.furnishedfinder.com/hc/en-us/articles/38788953573019-Understanding-What-Happens-When-Deleting-a-Tenant-Lead). The native history retention above preserves existing participant records and does not implement a lead restore path. No third-party UI styling or code copied.
