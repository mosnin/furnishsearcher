# Dated listing performance

Primary reference: https://support.furnishedfinder.com/hc/en-us/articles/34672767306907-How-Can-I-Track-Views-or-My-Listing-Performance. The current guide distinguishes ninety-day impressions/views/saves/shares from booking requests, direct inquiries, phone reveals, matched/unmatched tenant leads, reviews and map eligibility. This implementation supplies the dated activity service and native counts described below; it does not claim every performance-panel feature is complete.

## Owner report

`/dashboard/landlord/analytics` provides complete portfolio activity or a specific current property/unit, seven/thirty/ninety UTC-day windows, a real daily chart, accessible data table and downloadable CSV. The property selector pages thirty records at a time. Private report queries read at most ninety-one indexed daily rows; they never enumerate the owner's message/save history. Atomic owner/day aggregates keep the portfolio report complete regardless of how many property pages have been loaded. Portfolio activity is attributed to the owner when recorded; a current per-property report uses the current owner. Ownership changes do not expose the previous owner's property-day records. Staff can inspect a specified property; another owner's ID is not a public portfolio selector.

Only accepted dated events populate the report. Collection starts with the first accepted event for that scope and mode. The first day may be partial. Earlier days are unavailable, and no lifetime counter is distributed across invented dates. A recorded zero means no accepted observations/events, not verified absence of visitors. Legacy listing view counters remain labeled historical/unverified and excluded from the chart. Test and production data are partitioned using the existing backend billing-mode authority. Both CSV data and filename identify the mode; CSV exports contain dates, coverage and numeric counts, not client references, contact information, titles or precise location.

Existing compatibility analytics endpoints now fail explicitly above fifty properties or one thousand historical conversation/save rows per property, rather than perform unbounded scans or return silently partial totals. Current clients use the paginated/indexed service. The compatibility totals have the original historical meanings and are not the new ninety-day series.

## Event definitions

- Search appearances: a search card at least halfway visible for one second, or an individually represented visible map pin/selected map-group space. Grouped spaces are not all counted from the group marker. Map changes, scrolling into view and page visibility changes re-evaluate observations.
- Listing views: a visible detail page after one second. The old unattributed `listings.incrementViews` mutation is retained as a no-op for older clients. Accepted new observations also update the legacy counter and native geospatial view-sort entries.
- Share actions: successful native browser share or clipboard-copy completion. Cancelled/failed actions do not record a share; completion does not prove delivery to someone else.
- Unmatched housing requests: the first permitted, calendar-compatible partial match of a request/rental-space pair. Both owner intake and traveler alternative-sharing choices must allow it. Repeated scans, retries, later opt-out or reclassification do not create another original event. A later exact match may produce a matched event for the same pair; the two counts are not mutually exclusive or unique-traveler totals.
- Phone number reveals: a successful native signed-in number-disclosure transaction for an opted-in, confirmed owner on an eligible published space. At most one per account/rental space/UTC day; staff and the owner are excluded. A count does not establish that a browser rendered the number, a call connected or a message was sent. Failed reveals add nothing.
- Saves added/removed: successful native favorite insert/delete transactions. Duplicate save/unsave retries do not create new events. A new save requires current publication authority. Owners and staff do not count their own save operations as traveler activity. These are actions during the period, not the current number of favorites or unique savers.
- Booking requests: actual validated inquiry creation after duplicate-date rejection.
- New traveler threads: the first traveler-created conversation, not each reply. Request-created threads and booking requests are separate, overlapping metrics.
- Matched housing requests: the first stored request/property match after native availability/price/pet matching. Scheduled retries do not duplicate the match. This does not imply that a notification was delivered or that a stay was accepted.

Native event counters update with their source transaction. They require no client-supplied day/count/owner/metric timestamp. Public browser observations can record only appearances/views/shares, recheck actual publication, exclude the signed-in owner/staff, and deduplicate by authenticated account or anonymous page reference, listing, kind and UTC day. A daily actor ceiling permits at most six hundred listing/kind keys. Requests batch at most twenty-four IDs. Native identities determine signed-account deduplication even if page references rotate. Anonymous references can reset and are not bot-resistant unique identities; the report makes no claim otherwise. Counts are accepted observations, not independently verified human traffic. Auth loading waits before observation so signed-in owner previews are not intentionally sent as anonymous traffic.

Browser observations respect Do Not Track and Global Privacy Control and do not set a cookie/local-storage identifier. The page reference lives in memory; the backend stores only its hashed scope plus bounded deduplication keys. No IP, user-agent, message content, search criteria, recipient or precise location is stored in these records. These browser controls do not suppress operational counts from a user's explicit native save/inquiry/message/request transaction.

Daily aggregates become eligible for bounded cleanup before the start of the ninety-day UTC window, and observation deduplication records after two earlier full UTC days. Scheduled continuation handles batches of one hundred rows per table. First-collection metadata is retained without daily traffic or visitor references. Deletion/retention operations for the broader marketplace remain a separate open release requirement.

## Phone-reveal collection, 2026-10-25

The native phone reveal transaction now updates the property/day and owner/day counts atomically with the existing daily disclosure allowance. Concurrent retries disclose the same number without additional counts; failed requests and staff/self requests add no performance event. No phone number, caller account, contact consent or raw request is added to the private aggregate report or CSV. The account/day allowance is global to the deployment and survives a same-day environment-mode change; changing configuration does not permit replaying an earlier disclosure into the new mode. Old rate metadata is not backfilled into analytics.

Phone collection has its own optional first-event timestamp for each property/owner/environment scope. Existing daily rows and collection states remain valid without phone fields. Older phone values are normalized for storage compatibility but stay unavailable in the UI and blank in CSV until this separate start date. The first phone-collection day may be partial. CSV adds a Phone reveal coverage column so a recorded view count on a date cannot imply recorded phone history. New phone counts never rewrite the first collection date of the original eight metrics. The chart, cards, table and export respect the separate coverage.

Three additional focused integration cases cover old rows without the new field, mixed per-metric coverage, concurrent exact counts in property/portfolio, CSV blanks and explicit coverage, staff/failed/spoofed events, new callers/days, private-owner isolation and production/test separation. The full suite is now 293 tests across 30 files. The guarded native phone-contact smoke now verifies exactly one count for concurrent successful local disclosures and both property/portfolio collection metadata. Real Clerk SMS, successful hosted number disclosure, nonzero hosted phone chart and production operating acceptance remain open.

## Unmatched-lead collection, 2026-10-25

The matching transaction now records a new first partial request/rental-space pair in both the property/day and owner/day aggregates. It follows existing publication, geographic, full-date/calendar, block and consent checks before recording. Old unmatched candidates are not reconstructed into dates or counted on a routine rescan. The same first-partial timestamp deduplicates retries and transitions across later days. Closed requests and disabled intake stop new delivery but do not erase truthful historical activity. Portfolio counts sum pairs over spaces, not distinct travelers or owner deliveries.

Unmatched activity has its own optional first-collection timestamp per owner/property/mode and a backward-compatible optional daily count. Its card/chart/table/export remain unavailable before that timestamp, independently of general and phone collection. CSV includes Unmatched lead coverage plus blank unknown values. First collection days may be partial. Contact fields, mismatch text, caller IDs and message bodies are not exported. Existing native request cards retain the current mismatch details; this metric counts the historical first partial match rather than current open leads.

Four additional cases cover concurrent scans, mixed legacy daily rows and metric start dates, accurate CSV blanks/coverage, transitions to matched and back, closure/history retention, missing sharing permission, blocks/date conflicts, private and mode isolation, spoofed browser counters and absence of reconstruction from old unmatched candidates. ## Server-selected UTC windows, 2026-10-26

Acceptance exposed a clock mismatch: native queries selected a UTC range, but activity and map-eligibility charts/tables/exports rebuilt their dates using the device clock. A skewed clock could omit the actual rows or label other dates as recorded zero. An open subscription also did not intentionally requery at UTC rollover.

Both reports now return their exact `start`/exclusive `end` and `generatedAt` values. Shared report-series helpers use that returned window, never the device date. Cards, chart, table and CSV derive from the same activity series; eligibility uses its own returned native range. The UI shows the activity dates and native sample time explicitly. Unknown general/phone/unmatched/map history retains its existing blank/unavailable semantics.

The dashboard uses a fresh opaque random query key when mounted, focused or made visible, and schedules a rollover refresh from the native `end - generatedAt` duration. Device time does not schedule that duration or choose the report range. Refreshing also invalidates the selected response-rate and eligibility queries. No fixed polling loop, activity counter mutation, provider call or client-controlled metric time is introduced. The optional query key is ignored by native range/ownership logic; numeric keys remain accepted for the brief earlier development client. Returning from a throttled background tab triggers a fresh read. Rollover timing can lag by query/network/timer delay; the displayed checked time is the native sample time, not a promise of instantaneous collection.

Four additional tests cover 7/30/90-day activity and eligibility exports under device-clock changes, separate unknown phone/unmatched history, ignored client clock keys, and a native simulated UTC-midnight transition. Source tests prove the clock-skew/rollover behavior; hosted browser acceptance compares actual downloads with native records under the real current clock. It does not override the browser clock or claim to have waited through actual UTC midnight.

The guarded hosted probe reads the existing reserved owner only, pages its property choices and captures all 7/30/90-day portfolio and standing-property reports, with twelve expected CSVs stored privately outside the repository. It imports no fixture/contact/paid/identity authority and mutates no reporting data. Current positive portfolio activity is one previously recorded development traveler thread; it is not public marketplace traffic, a unique visitor, a phone disclosure or a confirmed booking. Anonymous activity and eligibility report reads are denied. The private native snapshot and sanitized receipt separate these scope limits.
