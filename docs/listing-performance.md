# Dated listing performance

Primary reference: https://support.furnishedfinder.com/hc/en-us/articles/34672767306907-How-Can-I-Track-Views-or-My-Listing-Performance. The current guide distinguishes ninety-day impressions/views/saves/shares from booking requests, direct inquiries, phone reveals, matched/unmatched tenant leads, reviews and map eligibility. This implementation supplies the dated activity service and native counts described below; it does not claim every performance-panel feature is complete.

## Owner report

`/dashboard/landlord/analytics` provides complete portfolio activity or a specific current property/unit, seven/thirty/ninety UTC-day windows, a real daily chart, accessible data table and downloadable CSV. The property selector pages thirty records at a time. Private report queries read at most ninety-one indexed daily rows; they never enumerate the owner's message/save history. Atomic owner/day aggregates keep the portfolio report complete regardless of how many property pages have been loaded. Portfolio activity is attributed to the owner when recorded; a current per-property report uses the current owner. Ownership changes do not expose the previous owner's property-day records. Staff can inspect a specified property; another owner's ID is not a public portfolio selector.

Only accepted dated events populate the report. Collection starts with the first accepted event for that scope and mode. The first day may be partial. Earlier days are unavailable, and no lifetime counter is distributed across invented dates. A recorded zero means no accepted observations/events, not verified absence of visitors. Legacy listing view counters remain labeled historical/unverified and excluded from the chart. Test and production data are partitioned using the existing backend billing-mode authority. Both CSV data and filename identify the mode; CSV exports contain dates, coverage and numeric counts, not client references, contact information, titles or precise location.

Existing compatibility analytics endpoints now fail explicitly above fifty properties or one thousand historical conversation/save rows per property, rather than perform unbounded scans or return silently partial totals. Current clients use the paginated/indexed service. The compatibility totals have the original historical meanings and are not the new ninety-day series.

## Event definitions

- Search appearances: a search card at least halfway visible for one second, or an individually represented visible map pin/selected map-group space. Grouped spaces are not all counted from the group marker. Map changes, scrolling into view and page visibility changes re-evaluate observations.
- Listing views: a visible detail page after one second. The old unattributed `listings.incrementViews` mutation is retained as a no-op for older clients. Accepted new observations also update the legacy counter and native geospatial view-sort entries.
- Share actions: successful native browser share or clipboard-copy completion. Cancelled/failed actions do not record a share; completion does not prove delivery to someone else.
- Saves added/removed: successful native favorite insert/delete transactions. Duplicate save/unsave retries do not create new events. A new save requires current publication authority. Owners and staff do not count their own save operations as traveler activity. These are actions during the period, not the current number of favorites or unique savers.
- Booking requests: actual validated inquiry creation after duplicate-date rejection.
- New traveler threads: the first traveler-created conversation, not each reply. Request-created threads and booking requests are separate, overlapping metrics.
- Matched housing requests: the first stored request/property match after native availability/price/pet matching. Scheduled retries do not duplicate the match. This does not imply that a notification was delivered or that a stay was accepted.

Native event counters update with their source transaction. They require no client-supplied day/count/owner/metric timestamp. Public browser observations can record only appearances/views/shares, recheck actual publication, exclude the signed-in owner/staff, and deduplicate by authenticated account or anonymous page reference, listing, kind and UTC day. A daily actor ceiling permits at most six hundred listing/kind keys. Requests batch at most twenty-four IDs. Native identities determine signed-account deduplication even if page references rotate. Anonymous references can reset and are not bot-resistant unique identities; the report makes no claim otherwise. Counts are accepted observations, not independently verified human traffic. Auth loading waits before observation so signed-in owner previews are not intentionally sent as anonymous traffic.

Browser observations respect Do Not Track and Global Privacy Control and do not set a cookie/local-storage identifier. The page reference lives in memory; the backend stores only its hashed scope plus bounded deduplication keys. No IP, user-agent, message content, search criteria, recipient or precise location is stored in these records. These browser controls do not suppress operational counts from a user's explicit native save/inquiry/message/request transaction.

Daily aggregates become eligible for bounded cleanup before the start of the ninety-day UTC window, and observation deduplication records after two earlier full UTC days. Scheduled continuation handles batches of one hundred rows per table. First-collection metadata is retained without daily traffic or visitor references. Deletion/retention operations for the broader marketplace remain a separate open release requirement.

## Evidence and remaining acceptance

Twelve focused cases cover observation deduplication/concurrency, actor limits and metric spoofing, current publication, owner/staff exclusion, old-counter inflation, signed-reference rotation, private permissions, paginated units, mode/ownership isolation, source save/inquiry/thread/match idempotency, complete portfolio aggregation, compatibility caps, missing-day/CSV semantics and bounded cleanup continuation.

`scripts/local-performance-smoke.mjs` refuses hosted/non-anonymous targets and real billing/email configuration. It uses explicitly synthetic local publication/payment/identity prerequisites and privileged QA identities. The actual running Convex backend accepted exactly one of all eight metric kinds for the new fixture, excluded owner previews, suppressed duplicate observations/saves/inquiries, denied anonymous/foreign report reads and processed an actual scheduled housing match. The result is `docs/evidence/local-performance-smoke.json`. This does not prove paid-provider, Clerk human sign-in, real visitor measurement or production operating scale.

Phone reveals, unmatched-lead explanations, continuous historical map-eligibility days, complete live multi-account/mobile UI/CSV acceptance, provider effects and whole-product production acceptance remain open. Current property reviews are already available through the existing moderated review flow; the new activity chart does not fabricate review/eligibility history. No new packages, external skills, reference UI styles or copied clone code were acquired.

Actual cloud acceptance with the existing synthetic Clerk account and a real provider-issued JWT now confirms private property/portfolio report access, anonymous report denial, hidden-property observation rejection and absent-history semantics. The QA property remains unpublished without fabricated billing/identity prerequisites. Its saved unapproved status can be pending while publication intent is off; public readiness and actual anonymous access were checked separately. Receipt: `docs/evidence/hosted-performance-auth.json`.

The existing reserved Clerk test-email account also completed the actual browser email-code sign-in using Clerk's documented development OTP (https://clerk.com/docs/guides/development/testing/test-emails-and-phones); no verification email was sent and no password, sign-in policy or bot protection was changed. The private hosted portfolio/property report, 7-day selection, metric selector, daily table and actual CSV download were exercised. Export bytes contain seven UTC dates, test mode and blank unavailable values. A 390px responsive check exposed clipping; the dashboard sizing fix was deployed and rechecked with document/main widths all 390px even with the table expanded. The viewport was reset and desktop rechecked. Receipt: `docs/evidence/hosted-performance-browser.json`. This is automated synthetic browser authentication/report/export acceptance, not real-person email/SMS ownership or nonzero hosted traffic/graph acceptance.
