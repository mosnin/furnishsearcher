# Clerk contact-change reconciliation

The existing confirmation UI remains backed by Clerk and the native `/contacts/confirm` route. This addition handles primary contact changes made outside that UI, so a saved native email/phone confirmation and phone-sharing consent do not simply remain valid until their thirty-day expiry after a provider change.

Research checked October 25, 2026: Furnished Finder's [email update](https://support.furnishedfinder.com/hc/en-us/articles/36530980962843-Updating-and-Verifying-Your-Account-Email-Address) and [phone update](https://support.furnishedfinder.com/hc/en-us/articles/48466611169435-Updating-and-Verifying-Your-Phone-Number) workflows require verification of the changed contact and describe old-contact security notices. Clerk's [webhook delivery guidance](https://clerk.com/docs/guides/development/webhooks/overview) requires signature verification and handling duplicate, unordered events. This batch implements native contact-authority reconciliation. Provider SMS, old-contact security notifications and production account operations remain separate acceptance work.

## Receiver and authority

`POST /webhooks/clerk-contacts` on the Convex site origin uses the existing bounded raw-body/Svix verifier: signed delivery ID, timestamp, unmodified body, HMAC-SHA256, multiple rotation signatures and a five-minute signature tolerance. It accepts no more than 256 KiB. All configuration must be present and environment-aligned before it accepts any event:

- `CLERK_CONTACT_WEBHOOK_SECRET`: the exact Clerk/Svix endpoint signing secret, server-only.
- `CLERK_CONTACT_WEBHOOK_INSTANCE_ID`: the exact Clerk instance ID, not a hostname or public key.
- `CLERK_CONTACT_WEBHOOK_MODE`: `test` or `prod`, matching both native `CLERK_CONTACT_MODE` and `CLERK_EMAIL_MODE`.

Subscribe only to `user.created`, `user.updated` and `user.deleted`. Unconfigured/misaligned receivers return 503, invalid signatures 401, invalid/wrong-instance relevant events 400, unrelated signed events 204, and committed relevant events 200. Database failures return 503 for provider retry. No payload, token, signing secret, raw contact or metadata is logged or returned.

The parser requires complete primary-contact references and canonical verified values; null primary or unverified/null verification removes authority. It ignores all roles, public/unsafe/private metadata, names and profile values. A webhook never creates a native profile, changes its role, grants identity/billing status, confirms a contact, enables email or enables phone sharing.

Private `clerkContactSnapshots` stores one indexed snapshot per Clerk subject/environment, contact hashes, provider object/event high-water times, the latest delivery ID and deletion/uncertainty state. Older object versions are ignored; equal object versions use event time. Duplicate/equivalent snapshots do not repeat revocation. Contradictory snapshots with indistinguishable ordering revoke authority until a strictly newer snapshot arrives. A deletion is a permanent contact tombstone, including when delivered before native onboarding. Hashes are private operational data, not anonymous public analytics; erasure/retention policy still needs production review.

## Native effects

When an accepted snapshot removes, changes or unverifies a saved confirmed primary email, the native notification recipient/proof is cleared, its revision advances and message email turns off. Lead-email preference choices remain saved, but every send still requires current confirmed recipient proof. Changing the primary phone revokes phone proof, increments its revision and removes listing-phone consent. Existing housing-request consent bound to an old revision cannot expose the changed number. The saved profile phone, rental data, message history and agreement history are retained.

Both authenticated phone and email confirmation paths consult the latest provider snapshot. Fresh claims for a superseded primary, claims issued before a contact change, uncertain contact state and deleted contacts cannot regain authority. Returning to an old primary still requires fresh explicit confirmation. A newly confirmed phone does not restore prior listing-phone consent. Unchanged primary contacts do not extend proof lifetime or turn revoked preferences back on.

Clerk events are asynchronous. There can be a delay before successful delivery, and a failed/unconfigured receiver does not provide immediate provider-change revocation. Monitor failures and replay missed events through the provider. Existing proof expiry and in-app revocation remain in effect. This receiver is not full native account deletion, data erasure, subscription cancellation, session revocation or account offboarding; those workflows require separate review/acceptance.
