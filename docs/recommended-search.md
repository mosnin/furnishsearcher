# Recommended search and versioned map ordering

Furnished Finder documents [response rate as a search-placement factor](https://support.furnishedfinder.com/hc/en-us/articles/52699055726363-What-is-the-Response-Rate). It does not publish the complete ranking formula. Furnishsearcher's explicit Recommended option uses its own declared policy: round `100 × (onTime + 1) / (received + 2)` to a whole percentage band, then use original creation time to break ties. A rental with no measured conversations starts neutral at 50; one unanswered first conversation lowers its band, and a first reply within 24 hours raises it. The prior limits one conversation's effect. Recency cannot move a rental across response bands. Editing a listing, views, subscription tier and unverified featured flags award no ranking credit.

Existing default and explicit Newest, price and Most viewed order remain separate. Recommended criteria persist through the shared URL, saved-search and alert validators. Public copy explains measured reply history, recency and a neutral start; it does not expose an owner's private percentage or internal score.

A private `listingRecommendations` row indexes each listing by status/score, normalized city/score and group/score. Its owner binding is checked against the current rental. List queries page that global index, not a resorted first result slice. The geospatial index uses the same score. Exact score ties do not promise a relative order across different indexes. Every returned card still passes current native publication, paid/identity/moderation, owner, dates/calendar, occupancy, amenities and location filters. No score is added to public listing/card responses or client-editable listing fields. Missing/incomplete source adoption withholds Recommended results instead of presenting a partial ranking as complete.

First-message and first-reply changes update the projection in the native message transaction. Native listing/location/publication changes refresh it, and deletion removes it. A reset queues a bounded owner refresh; the existing hourly response worker recomputes all rental spaces in 20-row pages so the UTC rolling window remains current. Reset and window refreshes are eventually reflected in ordering, rather than a promise of immediate portfolio-wide reordering.

## Spatial dependency repair

The installed official [`@convex-dev/geospatial` 0.2.1](https://www.npmjs.com/package/@convex-dev/geospatial/v/0.2.1) has a [reported numeric-key encoding defect](https://github.com/get-convex/geospatial/issues/50). The installed source confirmed that float bytes were written little-endian before lexicographic encoding; tests reproduced incorrect spatial order. This affects signed timestamps, prices and fractional recommendation scores, not just the new option.

The primary package is pinned to 0.2.1 and `scripts/patch-geospatial-order.mjs` changes the two endian constants in `src/component/lib/tupleKey.ts` and its built `dist/component/lib/tupleKey.js` to big-endian. Original/patched SHA-256 hashes guard the exact files, the patch is idempotent and file replacement avoids mutating package-manager hardlinks. It runs on postinstall. The package's Apache-2.0 and embedded d64 license notices remain intact; registry integrity is locked in package-lock.json. This is a dependency repair; no external skill is acquired.

A separately installed, unmodified npm alias `geospatial-legacy` retains the original component under its existing `geospatial` name. The corrected component uses a new `geospatialV2` namespace; existing encoded rows are never reinterpreted in place. New spatial cursors are prefixed `geo2:`. Existing unprefixed cursors continue through the old component and its original ordering until the search refreshes; current card eligibility is always rechecked. The original package-file hashes are verified on every patch run.

`geo.reindex` adopts eight listings per page and records a durable migration cursor. New spatial searches wait until adoption completes. Version checks restart stale pre-v2 jobs safely, duplicate cursor jobs do not regress progress, and an hourly recovery worker resumes an interrupted adoption. Normal changes then maintain v2. `geo.indexStatus` and `recommendations.status` provide actual native readiness. Initial rollout runs `geo:reindex` with a null cursor and `recommendations:refreshPage` with a null cursor after response-source adoption, then verifies both statuses. These operations target development here; production is unchanged.
