# Listing photo removal and storage cleanup

Furnished Finder's [photo editing guide](https://support.furnishedfinder.com/hc/en-us/articles/41355315965339-Editing-Your-Photos), checked October 25, 2026, supports removing/replacing photos and galleries of up to thirty images. Furnishsearcher's existing editor already saves those changes. This batch adds cleanup of the underlying registered uploads. The seven-day recovery period is our implementation choice, not a claim about Furnished Finder's retention policy.

An authenticated new upload receives a seven-day unused deadline. Creating or saving a gallery adds native references in the same transaction as the listing change and clears that deadline. The same owned upload can be used by multiple spaces. Removing a photo or deleting a listing removes only that listing's reference; the final removal starts a new seven-day period. Saving the photo again before collection clears the deadline. Reordering/caption changes, failed saves and unauthorized writes do not remove another listing's reference. Hidden, incomplete and inactive listings retain their saved photos.

Daily maintenance runs in bounded transactions of up to twenty-five uploads/listings and schedules continuations. A file becomes eligible after seven days; actual collection happens on maintenance, rather than at an exact seven-day instant. The collector rechecks references and profile-image registration in the same mutation as byte deletion. If a concurrent save wins, its reference protects the file. If deletion wins, saving the expired upload fails validation and requires a fresh upload. An already missing object does not prevent registry cleanup. Storage deletion uses Convex's [native storage operation](https://docs.convex.dev/file-storage/delete-files).

## Existing data

Before deletion is permitted, maintenance builds a private exact-URL hash lookup from registered native storage and walks every listing with a persistent cursor. It records canonical storage IDs and recognizes old URL-only galleries only by matching a registered object's actual native URL. Serving URLs contain a different UUID from the native storage ID, so parsing a URL does not establish ownership or identity. URLs remain read-derived; the auxiliary hash is a migration lookup, not the canonical image source.

Legacy upload adoption happens after reference discovery completes. Unused legacy uploads receive a fresh seven days from adoption, irrespective of their original age. Existing galleries are not purged because they predate this feature. Oversized/corrupt galleries or ambiguous upload registrations stop the migration before deletion; they require repair. Cron re-entry resumes the stored cursor. Public clients cannot supply collection time, force expiry or invoke maintenance.

This collector covers registered listing-photo uploads. It does not scan arbitrary storage, fetch/delete external images, erase accounts, apply a document-retention policy or remove profile/pet pictures. A storage object lost before upload registration during a process crash needs separate unregistered-object reconciliation. Copied public URLs and already downloaded images cannot be recalled. No new editor undo/history UI was added; native reattachment remains valid during recovery.

## Evidence

- `tests/photo-retention.test.ts`: eight cases cover seven-day boundaries, shared/hidden spaces, recovery, failed/unauthorized writes, stale expiry guards, rental deletion, 52-listing legacy migration, 56-upload cleanup, missing bytes, unrelated/profile storage and racing save/cleanup.
- Full suite: 359 tests / 34 files, TypeScript and Next production build pass.
- Twenty-third guarded local flow: `scripts/local-photo-retention-smoke.mjs` verifies actual HTTP uploads and bytes, native migration, shared canonical/legacy URL references, grace/reuse, real byte deletion and expired-save rejection. Only a new reserved synthetic fixture's unused deadlines are aged by a temporary guarded helper. The helper is removed and the real app re-pushed before the script returns. Seven real days were not elapsed. Receipt: `docs/evidence/local-photo-retention-smoke.json`.
- `scripts/hosted-photo-retention-smoke.mjs` verifies the dedicated Clerk development instance and absent Resend key, then uses the reserved synthetic account's real JWT for HTTP upload, exact-byte checks, private save/hydration, anonymous denial, shared-reference protection, seven-day deadline and recovery. It deletes only its own new unpublished test listings; their bytes remain until natural expiry. No cloud deadlines are forced. Receipt: `docs/evidence/hosted-photo-retention.json`.

Convex remains the backend. The preview's development schema/functions and daily cleanup are deployed. Production settings, real email/SMS and customer files were not changed. Hosted browser editing, real seven-day elapsed collection, unregistered storage reconciliation, legacy external-image migration and broader product acceptance remain open.
